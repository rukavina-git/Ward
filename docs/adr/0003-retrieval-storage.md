# 3. Retrieval storage

Date: 2026-11-21
Status: Accepted

## What is this
Where Ward keeps its chunks and their embeddings, and how a search finds
the closest ones. At large scale this is the job of a vector database,
which uses an approximate index to search millions of vectors quickly.
Ward's corpus is small, so the question is whether it needs one at all.

## Context
- **Corpus size** (council estimate from the GitHub API, to be confirmed at
  ingestion):
  - MASTG is about 3.6 MB of Markdown in 1,079 files; MASVS is about 94 KB.
  - That's roughly 1M tokens and about 2,500 chunks.
- **Index size:** 2,500 chunks × 384 dimensions is about 3.8 MB as 32-bit
  floats, or about 1 MB as 8-bit integers. Dimensions depend on the model
  (ADR 0004).
- **Where it's searched:** the index is read on the user's machine by the
  MCP server (offline, no keys) and in the browser by the website. Neither
  can depend on a hosted service (ADR 0001).
- **Citations:** every citation must link back to its source, so each
  chunk carries its source URL, version and licence (CLAUDE.md
  conventions).
- **Licence:** MASVS and MASTG are CC BY-SA 4.0.

## Options
- **Index file shipped with the package, searched in memory.** Cost: $0.
  - How: chunk text and metadata as JSON plus the vectors in a binary
    file, loaded at start. Vector search compares the query with every
    chunk by cosine similarity (brute force). Keyword search uses a BM25
    index, also built by hand.
  - Pro: works offline, and the same file works in the browser.
  - Pro: brute force is exact and takes about a millisecond at this size.
  - Pro: every part is built by hand, which is the learning goal.
  - Con: doesn't scale to millions of chunks, and there's no SQL.
- **Postgres + pgvector.** Cost: $0 on Neon's free plan (1 GB storage per
  project, 100 compute-hours a month, per Neon's FAQ updated 2026-10-01).
  - Pro: real database skills, and SQL filters.
  - Con: every query needs the network and credentials. That's a hosted
    backend, which ADR 0001 ruled out, and it adds a running service.
- **SQLite + sqlite-vec + FTS5, shipped as one file.** Cost: $0.
  - Pro: SQL, and BM25 keyword search built in.
  - Con: needs a native module in Node and a WebAssembly build in the
    browser.
  - Con: FTS5 does the keyword search for us, so we'd learn less.
- **A hosted vector database (Pinecone, Turbopuffer and similar).** Not
  priced: free tiers exist, then usage-based billing.
  - Con: like pgvector, it needs the network and a key for every query,
    which rules it out regardless of price.

## Decision
An index file shipped with the package, with brute-force vector search
and hand-built BM25 keyword search.

What the index records:
- **Index level:** format version, corpus version, embedding model id,
  dimensions, build date.
- **Per chunk:** source id (e.g. MASTG-TEST-0233), section path, source URL
  at the pinned tag, source version, licence id, and the chunk text.
  Citations are built from these fields, never generated by a model.

**Licence handling.** This is flagged for the owner, because it affects
publishing.
- The chunks are adapted CC BY-SA 4.0 text. ShareAlike means the adapted
  text must stay under CC BY-SA 4.0 too. We treat the embeddings the same
  way, to be safe.
- The data folder ships with its own LICENSE (CC BY-SA 4.0) and a NOTICE
  that credits OWASP MAS, links the sources and says the text was split
  into chunks.
- The code stays MIT. `package.json` declares `MIT AND CC-BY-SA-4.0`.
- Every citation shown to a user or agent includes the attribution and a
  link.
- This is publishable. It only means the data part can never be relicensed
  as MIT.

## Consequences
- No database to run, back up or pay for. Search is the same code in the
  MCP server, the evals and the browser.
- Karlo builds keyword search, vector search and hybrid ranking by hand.
  Approximate indexes (such as HNSW) stay a concept for now.
- Revisit if the corpus grows past about 50,000 chunks (for example with
  iOS and ASVS added). Options then: an in-memory approximate index, or
  sqlite-vec.
- docs/sources.md (plan 3) records each source's licence and attribution
  text.

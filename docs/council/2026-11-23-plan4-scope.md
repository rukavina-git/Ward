# Council: Plan 4 scope (2026-11-23)

Decision: **Owner (Karlo, 2026-11-23):**
- Q1 a: step 01 is the held-out set, target **30** issues (soft cap
  about 4 labelling sessions; if short, freeze and state the count).
  Bar and set hash committed before the first Claude-alone run.
- Claude-alone gate run on **Sonnet 5.5 and Opus 5.5**; later
  comparisons mainly Sonnet, Opus where the gate makes it interesting.
- Q2 a: all four analyzers, dependency check **last and cuttable**.
  Built by Ward, not by wrapping OSV-Scanner (no extra install for the
  user): download the fresh OSV Maven data at check time, match versions
  in our own code, stamp every verdict with the data date (ADR 0011).
- Q3 c: top-k plus matched query terms, no cutoff; results marked as
  reference text, not instructions.

## Brief

Decision: scope and order of Plan 4 (MCP server and analyzers).

Q1. What should step 01 of Plan 4 be?
- a) Held-out eval set first (real security-fix commits from OSS Android
  apps, decoys toward 30, "defensible" label), frozen, then run Claude
  Code alone on it against a bar written first (roadmap order).
- b) MCP server first (checklist, get_check, search over the existing
  BM25 index), eval set later in the plan.
- c) Analyzers first (merged manifest, network security config,
  targetSdk, deps vs OSV), since they are the plain-code core.
- d) Small held-out set (~10 commits) first, grow later in plan 6.

Q2. Which analyzers ship in plan 4?
- a) All four: merged manifest, network security config, targetSdk,
  dependencies vs offline OSV snapshot.
- b) Manifest + NSC + targetSdk only; OSV snapshot moves to a later plan.
- c) Manifest only; others driven by what the held-out eval shows Claude
  misses.

Q3. How does the MCP search tool handle "nothing relevant" (BM25 can't
separate no-answer queries; vectors didn't help)?
- a) Always return top-k with scores; the calling agent judges relevance.
- b) Build a cutoff signal now (score ratio, query-term coverage) tuned
  on the eval's none queries.
- c) Return top-k plus a coverage field (which query terms matched) and
  defer any cutoff to plan 6.
- d) Drop free-text search from the MCP server; expose only ID lookup
  and the checklist.

Constraints: no paid APIs, no runtime LLM calls (ADR 0007, 0001). RAG
pieces by hand. BM25 ships alone (ADR 0010). Plan 4 must end with Ward's
MCP tools usable from Claude Code. Code licences permissive only. Out of
scope: UI, privacy module, site. Open fact: how hard real OSS fix
commits are to label.

Files: PRODUCT.md, docs/roadmap.md, ADR 0009, ADR 0010,
docs/plans/knowledge-base/progress.md.

## Members

### AI engineer
VOTE: Q1 a, Q2 a, Q3 c

WHY:
- Q1: The held-out set only means something if it's frozen before any Ward code exists. It is also the go/no-go gate for analyzers (ADR 0009). Put a timebox on it: freeze whatever is labelled by a fixed date, at least about 15 cases, so the labelling-effort question has a hard ceiling.
- Q2: Dependency CVEs are the one miss the baseline actually showed (Gson). Dropping OSV keeps the easy analyzers and cuts the one with evidence behind it. To keep it small, check only declared direct dependencies and version catalogs. Leave transitive resolution out.
- Q3: In an agent loop, the calling model is already a strong reranker. A cutoff tuned on a dozen or so "none" queries would overfit. A coverage field is deterministic, gives the agent evidence it can cite, and costs nothing. ID lookup and the checklist are the main paths anyway.

RISK of my pick: The OSV snapshot adds a licence check per source (OSV aggregates several), a refresh job and Gradle parsing. That could push the MCP server past the end of the plan, so build the MCP server before the OSV analyzer.

I'D VETO: Q1 d and Q2 c. Growing the held-out set after checks exist, or choosing analyzers by what Claude misses on the held-out set, both tune against it. That breaks "never tune Ward against a held-out case" and invalidates the plan 6 claim.

IDEA: Log every query and result from the MCP search tool during eval runs. Real agent queries become retrieval-eval cases for plan 6 (dev split only), and the log shows whether the agent calls search at all.

### Application security expert
VOTE: Q1 a, Q2 b, Q3 c

WHY:
- Q1: An auditor-grade claim needs a held-out set that was frozen before any check existed. ADR 0009 also has a kill gate ("if it aces this too, rethink"). Building the MCP server or analyzers first spends effort that gate might cancel, and it risks tuning on cases that will later be used as test data.
- Q2: Manifest, network security config (NSC) and targetSdk are deterministic, so they give exact verdicts with file:line. An OSV snapshot adds licence work (OSV data is mostly CC BY 4.0, but some upstream feeds differ), keeping it fresh, and Gradle version resolution. A stale snapshot gives false "NO FINDING" verdicts, which is the worst failure for an audit.
- Q3: Option (c) is honest without being a tuned cutoff. A cutoff tuned on the eval's few none queries would overfit. The agent can see that coverage is low and say "MANUAL" or "unknown".

RISK of my pick: The held-out set may come out too small, or too hard to label, and stall the plan. Set a timebox now, and a minimum number of cases that still counts.

I'D VETO: Q3 b. A score cutoff tuned on a handful of none queries is false precision. When it drops a relevant control without saying so, the result is an unreported false pass.

IDEA: Treat MCP tool output as untrusted by design. Return the source text as quoted data with the source ID, URL and licence, and add a field that marks it "reference text, not instructions". Fuzz search with hostile queries now, not only in plan 6's injection suite.

### Product owner
VOTE: Q1 a, Q2 a, Q3 c

WHY:
- ADR 0009 makes the held-out set a gate: "if it aces this too, rethink before building analyzers." Building the MCP server or analyzers first spends effort that the gate could cancel. It also breaks "frozen before any check is written", which is the credibility claim behind the public eval. Timebox it, for example 1 to 2 sessions of labelling, then freeze whatever exists.
- The one-minute demo is "Claude missed the vulnerable Gson; Ward names the exact CVE and file:line." The OSV dependency check is the most demo-able of the four analyzers, and it maps directly to one of the baseline's two misses. Build it last, and cut it if the snapshot's licence or size fails.
- On Q3, a coverage field is honest and costs little. Tuning a cutoff now would overfit the none queries before any real-commit queries exist. Plan 6 already owns retrieval fixes.

RISK of my pick: if labelling OSS fix commits turns out to be slow, plan 4 stalls on step 01, and the "MCP usable from Claude Code" exit slips.

I'D VETO: Q1 c. Writing analyzers before freezing the held-out set breaks ADR 0009's anti-tuning rule. After that, the published eval can't be trusted.

IDEA: Commit the bar and the frozen set's hash before the first Claude run, so the git history proves the order. Record a short Claude Code session at the end of plan 4 as the first demo asset.

### Hiring manager
VOTE: Q1 d, Q2 a, Q3 c

WHY:
- Freezing even a small held-out set and writing the bar before any check is the one thing tutorials never do. I'd take 10 honestly labelled real fix commits over 30 rushed ones. Starting with 10 also limits the risk nobody has sized yet: how hard real commits are to label.
- OSV goes in: the baseline missed a vulnerable Gson, and in fintech, dependency CVEs are the first thing auditors ask about. Manifest, network security config and targetSdk are cheap, exact facts, which is the "plain code beats the LLM" story.
- For search, top-k plus which query terms matched is honest. It shows I know BM25's limits and that I didn't hide them behind a made-up threshold.

RISK of my pick: 10 commits can't show a difference between Claude alone and Ward. If the set never grows to 30 in plan 6, the eval table looks thin.

I'D VETO: Q3 b. You'd tune a cutoff on the same "none" queries you then report on, which is test leakage. A reviewer who spots that stops trusting every other number on the page.

IDEA: End plan 4 with a recorded, unedited transcript of Claude Code calling Ward's tools on one held-out CVE commit: verdicts, citations and the "couldn't verify" list. That's the artifact I'd actually open in my 3 minutes.

### Developer user
VOTE: Q1 d, Q2 b, Q3 c

WHY:
- My audit is next month. What I need from Ward is a report an auditor will accept, and the evidence is what makes it acceptable. A small frozen held-out set of about 10 commits keeps the claim honest without holding plan 4 up for weeks while real fix commits get labelled, which nobody has costed yet. It can grow to 30 in plan 6.
- Manifest, NSC and targetSdk have exact answers. They are where I can't trust Claude Code to give the same answer twice ("is cleartext allowed for this domain in the *merged* manifest?").
- On dependency CVEs, Dependabot, Renovate or `./gradlew dependencyCheck` already warn me. An offline OSV snapshot needs refresh work and goes stale. It can come later.
- For search, my agent can judge relevance if Ward shows which of my query terms actually matched. A hidden cutoff tuned on a few "none" queries would drop real hits without saying so.

RISK of my pick: about 10 commits can't show a false-alarm difference with confidence. The plan 4 numbers will be weak, so call them a smoke result, not proof.

I'D VETO: Q3 d. Dropping free-text search leaves me unable to ask "what applies to WebView file access?" unless I already know the MASVS ID, and I don't.

IDEA: a `coverage` tool that lists every in-scope control that still has no verdict. That list is what I'd hand my auditor, and it fits the "explicit verdict for every control" claim.

### Cost and operations
VOTE: Q1 d, Q2 b, Q3 c

WHY:
- Q1: Labelling real fix commits by hand is the unknown cost, and every Claude-alone run uses up Pro-plan 5-hour quota. About 10 frozen commits, with the bar written first, still gives the go/no-go signal. If Claude aces them, nothing has been sunk into labelling 30.
- Q2: OSV is the only analyzer with ongoing upkeep: snapshot freshness, download size, per-source licences (CC BY 4.0 plus others), and a refresh job. A stale snapshot produces false passes, which is exactly the metric Ward stakes its claim on. Manifest, NSC and targetSdk are pure code with no data to maintain, only the MASTG pin.
- Q3: c costs nothing and keeps a later cutoff possible. Tuning a cutoff on a handful of "none" queries now would overfit, the same trap ADR 0010 avoided.

RISK of my pick: 10 commits is noise-level. Plan 6 has to add more cases blind (never looking at Ward's checks), or "held-out" becomes weak.

I'D VETO: Q2 a if the snapshot isn't dated. A "NO FINDING" from an undated, stale vulnerability database is a false pass that looks like evidence. That breaks ADR 0009's promise.

IDEA: When dependency checks do arrive, wrap OSV-Scanner's offline mode (Apache 2.0, local DB) instead of maintaining a snapshot ourselves. Stamp every analyzer verdict with its data version (MASTG pin, OSV date), and have the MCP server warn when that data is older than N days.

**Agree.** Q3 c, unanimous: top-k plus a matched-terms coverage field,
no cutoff yet. Nobody wants the held-out set later than step 01 (b and c
got no votes).

**Split.** Q1, a vs d, 3–3. Both sides want the same thing: frozen first,
bar written first, a cap on labelling effort. The real difference is
whether the set grows after checks exist. The AI engineer vetoes that,
and cost/ops says plan 6 additions must be blind. Q2, a vs b, 3–3: OSV
is the analyzer with evidence behind it (the Gson miss) but also the only
one with upkeep and a stale-data false-pass risk.

**Vetoes.** Q3 b (AppSec, hiring manager): tuned cutoff = leakage and
silent false passes. Q1 c (PO). Q1 d and Q2 c (AI engineer): growing or
selecting by the held-out set tunes against it. Q3 d (developer). Q2 a
with an undated snapshot (cost/ops).

**Ideas worth keeping.**
- Commit the bar and the frozen set's hash before the first Claude run (PO).
- MCP output marks source text as reference data, with ID, URL, licence;
  fuzz search with hostile queries now (AppSec).
- Stamp every analyzer verdict with its data version (MASTG pin, OSV
  date); warn when stale (cost/ops).
- Consider wrapping OSV-Scanner offline (Apache 2.0) over our own
  snapshot (cost/ops). Not "built by hand", but it isn't RAG, so the
  hand-built rule doesn't apply.
- A `coverage` tool listing in-scope controls with no verdict (developer);
  fits plan 5's report but the tool can start here.
- Log MCP search queries during eval runs, as dev-only cases for plan 6
  (AI engineer).
- End plan 4 with a recorded, unedited Claude Code run on one held-out
  commit (HM, PO).

**Recommendation.**
- Q1: **a, timeboxed.** Step 01 is the held-out set: target 30, freeze
  whatever is labelled after a fixed budget (e.g. 2 sessions), floor 15.
  Commit the bar and the set's hash before the Claude-alone run. Any
  plan 6 additions are labelled blind, in a separate frozen batch.
- Q2: **a, with OSV last and cuttable.** Order: manifest, NSC, targetSdk,
  then MCP server, then OSV (direct deps and version catalogs only,
  dated data, cut if licence or size fails).
- Q3: **c.** Plus the untrusted-text marker on every tool result.

**Only the owner can decide.**
1. The labelling budget and floor (2 sessions / 15 cases?).
2. OSV in plan 4 (cuttable, last) or moved later.
3. If OSV stays: wrap OSV-Scanner, or build the lookup ourselves on a
   dated OSV export. OSV data is CC BY 4.0 (to confirm per source in
   docs/sources.md).

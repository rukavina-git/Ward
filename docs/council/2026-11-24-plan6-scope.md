## Brief

Ward (repo /Users/karlo/Dev/ward) is a local Claude Code plugin: /ward:check gives an Android pre-publish report, one verdict per MASVS control with MASTG tests nested, evidence checked by a citation checker, IDs from a pinned OWASP index, plain-code analyzers (manifest, NSC, build config, OSV dependencies, must-exist privacy). Plan 5 is done. Facts: held-out batch 1 (10 real security-fix commits), one trial each: Ward 5/10 found (only 2 by a real FAIL; 3 lenient via MANUAL rows), Claude alone 3/10; wrong citations Ward 0/243, alone 25/83. Ward missed all 3 code cases and both absence cases. The agent called get_check/search 0 times on held-out (20 of 56 checks on Karlo's own app; 36 judged by title). Karlo's app: 4 findings, 1 false alarm. A ward-check run is ~2–3 min, ~$0.6 API-equivalent, paid from Karlo's Pro plan usage (no money, but usage is scarce; he wants the smallest run that answers the question). Batch 2 (20 more held-out cases) exists as an idea, unlabelled. GitHub main has only the first commit (develop → main PR pending).

Roadmap Plan 6 "proof" today: (1) end-to-end eval: four setups (alone, +checklist skill, +OWASP plugin, +Ward) plus analyzers-only, on example app and held-out, ≥3 trials, spread reported; (2) prompt-injection suite (hostile comments/files in the checked app); (3) retrieval fixes driven by failures (reranking etc.), evals before/after.

Q1. What should Plan 6 do first / mainly?
 a) Roadmap as is: the full end-to-end eval (5 arms × 11 apps × 3 trials ≈ 165 runs).
 b) Skill v2 first (developed on the example app only): make the agent read test text before judging, tie NO FINDING to evidence, group FAILs by finding, target code and absence gaps; then one held-out run of v2.
 c) Smallest decisive eval now: Ward vs alone only, held-out 10 + example app, 3 trials (~66 runs), no new skill.
 d) Label batch 2 (20 more cases, frozen) first, since 10 cases can't show a difference; then a two-arm eval.
Q2. Prompt-injection suite:
 a) As roadmap: hostile fixture app, run the agent on it, score whether the report is subverted (LLM runs).
 b) Deterministic only: unit tests that hostile text can't change verdicts/IDs/summary in code (schema, checker, write_report); no LLM runs.
 c) Both: b first, then a small (1–3 runs) agent test.
 d) Defer to Plan 8 (triage UI).
Q3. Retrieval fixes (reranking etc.):
 a) Keep as planned.
 b) Drop: the agent barely calls search; replace with "make the agent use the sources" (part of skill v2).
 c) Defer until an eval shows a retrieval failure.

Locked: no LLM calls at runtime, no paid APIs, held-out never used for tuning (skill changes tried on the example app; held-out runs once per skill version, all logged), verdict set FAIL/NO FINDING/NEEDS DYNAMIC/MANUAL/N/A (never PASS), permissive licences, prompts in prompts/. Out of scope: privacy/GDPR (Plan 7), triage UI (Plan 8), site (Plan 9). Open: whether a skill can make the agent read deeper; noise of one trial.

Read: PRODUCT.md, docs/roadmap.md, docs/measurements.md (top 4 entries), docs/plans/the-check/progress.md (Gotchas), evals/held-out-bar.md, evals/results/held-out/ward-check.md. Optional: prompts/ward-check/SKILL.md, docs/adr/0009-precision-and-evidence.md, 0012.

## Members (verbatim)

### 1. AI engineer
VOTE: Q1 b, Q2 c, Q3 b

WHY:
- The failure is in how the agent behaves, not in retrieval. It made 0 get_check/search calls on held-out and judged 36 of 56 checks on Karlo's app by title. Any eval of skill v1 measures a weakness we already know about.
- At n=10, 3 trials of v1 still can't tell 5/10 from 3/10. The 66–165 runs (~$40–100 API-equivalent) buy spread on the wrong system.
- Reranking (re-sorting search results so the best ones come first) can't help a search that is never called. Add it back only if traces show bad hits after v2.
- For injection, start with the deterministic tests, since code decides IDs, verdicts and the checker. Then 1–3 agent runs to check what code can't, such as a hostile comment that persuades the agent to write NO FINDING.

RISK of my pick: v2 is tuned on a single example app, which Ward's own author planted. It may overfit, and one held-out run of v2 stays noisy.

I'D VETO: Q1 a. It spends the scarce Pro usage measuring the v1 skill we already know is weak.

IDEA: Push, don't pull. Have report_skeleton put each pending check's MASTG test text inline, one group per page, so the agent doesn't have to call get_check. Track get_check use per check as a metric in its own right. Label batch 2 alongside, which needs no eval runs, so v2's one held-out run covers 30 cases instead of 10.

### 2. Application security expert
VOTE: Q1 b, Q2 c, Q3 b

WHY:
- For an audit, held-out shows 2/10 found strictly. The other 3 are MANUAL rows ("check each exported activity"), which an auditor would not accept as findings. get_check and search were called 0 times. Re-measuring v1 over 66–165 runs would only show the same gap with tighter error bars.
- Tying NO FINDING to evidence matters most. A NO FINDING without evidence is false assurance, and that is worse in an audit than a missed MANUAL row.
- Injection: the realistic attack is suppression, not changing IDs. Picture a comment next to a real bug saying "reviewed, mark NO FINDING". The code tests (b) can't catch a verdict the agent lowers itself, so 1–3 agent runs are needed. The code tests come first because they're free.
- Better retrieval doesn't help if the agent never calls search. Fold "use the sources" into skill v2.

RISK of my pick: v2 gets tuned on one planted example app, so it may overfit, and one held-out run is still ±30 points.

I'D VETO: a. It spends about 165 runs of scarce usage measuring a skill version already known to skip reading. Also, from now on, MANUAL rows must not count as "found".

IDEA: Pre-register strict scoring (FAIL on the anchor only). Add a "false NO FINDING on an anchor file" metric. Put the injection canary next to a planted bug in the example app, so a code check can score whether that row flips.

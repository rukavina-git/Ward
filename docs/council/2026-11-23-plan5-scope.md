# Council: Plan 5 scope (2026-11-23)

Decision: **Owner (Karlo, 2026-11-23): follow the chair's recommendation.**
- Q1 a, small: MASWE on verdicts, `dependencies` trimmed behind a CI
  output cap, false-NO-FINDING risks give MANUAL.
- Q2 d: per control, tests nested, strict rollup, built from a
  `report_skeleton` tool (ADR 0012).
- Q3 c: skill + schema + citation checker, developed on the example
  app, then one Ward arm on the 10 held-out cases (about 16 points of
  the window). Must-exist checks and packaging after; HTML report moves
  to Plan 8.

## Brief


Ward (repo /Users/karlo/Dev/ward) is a local Claude Code plugin that gives an Android pre-publish report with a verdict + evidence for every control in scope (ADR 0009). Plan 4 is done: MCP server with knowledge tools (checklist, get_check, search) and plain-code analyzers (manifest, network/NSC, targetSdk+debuggable, dependencies via OSV). One Ward-arm run on held-out case HO-04 found it (Claude alone missed it) but the agent never used search/get_check/checklist and got 4 of 5 MASWE IDs wrong (verdicts carry MASTG IDs, not MASWE). Gate on 10 real held-out cases: Claude alone found 3/10, 25/83 citations wrong. Open carry-overs: several "false NO FINDING" risks in analyzers (reviewer SHOULDs), `dependencies` output 45 KB (cap ~25k tokens), meta/eval-runner nits.

Roadmap Plan 5 currently: skill + report JSON schema + /ward:check; must-exist checks (account deletion, privacy policy link, data-deletion URL); read-only HTML report; citation checker (cited IDs, file:line, quotes must exist); package as plugin, run on Karlo's own app. Plan 6 = end-to-end eval (≥3 trials, all arms) + prompt-injection suite.

## Questions
Q1. What comes first in Plan 5?
 a) Step 01 = hardening: MASWE IDs on every verdict, trim `dependencies`, fix the false-NO-FINDING SHOULDs; then the skill.
 b) Skill + report schema first; fix carry-overs inline as they bite.
 c) Push carry-overs to Plan 6 (eval-driven fixes).
Q2. Unit of "every control in scope" in the report:
 a) 24 MASVS controls (verdict per control, MASTG tests as evidence).
 b) MASTG tests in the chosen profile (~100+ static ones; many NEEDS DYNAMIC).
 c) MASWE weaknesses (77).
 d) Hybrid: per MASVS control, with per-test sub-verdicts nested.
Q3. Which Plan 5 items earn their place before the Plan 6 eval?
 a) All five as on the roadmap.
 b) Skill+schema, citation checker, must-exist checks, plugin packaging; HTML report moves to Plan 8 (triage UI).
 c) Skill+schema + citation checker only, then run a small Ward-vs-alone eval on the 10 held-out cases right away; must-exist, HTML, packaging after.
 d) Something else (say what).

## Constraints
Locked: no LLM calls at runtime, no paid APIs (LLM work via `claude -p` on a Pro plan; eval runs cost plan usage, ~1.6% of the 5-hour window per run), verdict set FAIL / NO FINDING / NEEDS DYNAMIC / MANUAL / N/A (never PASS), held-out set never used for tuning, permissive licences, stdout = MCP protocol. Out of scope: privacy/GDPR module (Plan 7), triage UI (Plan 8), website (Plan 9). Open facts: how reliably a skill makes the agent call Ward's tools; whether a schema-validated report reduces wrong citations.

## Members

### AI engineer
VOTE: Q1 a, Q2 d, Q3 c

WHY:
- Wrong MASWE IDs and false NO FINDINGs break the claim directly (ADR 0009: trust, no false passes). They are cheap, deterministic fixes. Trimming `dependencies` matters too: Claude Code warns on MCP output above about 10k tokens and cuts it at 25k by default, so 45 KB is borderline. A skill built on noisy tools measures the noise, not the skill.
- Q2 d: 24 verdicts are too coarse to audit, and 100+ test verdicts drown the reader in NEEDS DYNAMIC. Nesting per control keeps the report readable and the evidence traceable. The schema should require a MASWE ID on each sub-verdict.
- Q3 c: the two open facts (does the skill get Ward's tools called, does a schema cut wrong citations) decide everything after. Measure them first. HTML and packaging are presentation and teach nothing new.

RISK of my pick: if we run the held-out set early and then iterate the skill, we are tuning against it. Iterate on the example app and the MASTG demos. Run held-out once per skill version and log each run.

I'D VETO: Q1 c. Pushing false NO FINDINGs to Plan 6 means the eval scores known bugs, which is wasted plan usage.

IDEA: add a deterministic MCP tool `report_skeleton`. It returns every control and test in scope, with the analyzer verdicts and the correct MASWE IDs already filled in. The agent only fills the gaps and copies IDs instead of recalling them, so we rely less on the skill triggering.

### Application security expert
VOTE: Q1 a, Q2 d, Q3 c

WHY:
- ADR 0009 promises "fewer false alarms, without more false passes". A false NO FINDING is a false pass, and an auditor would treat it as the worst defect. Examples: isDebuggable set through `configureEach`, a flavor's NSC ranked above main's, an OSV index with 0 advisories. Fix these before the report puts its name on them. Leaving them "inline as they bite" means they never bite, because nothing flags a silent pass.
- An auditor's unit is the MASVS control, and MASTG tests are the procedure. Nesting per-test sub-verdicts (with MASWE IDs from the pinned index) lets a reviewer follow each control verdict down to its evidence. Per control only (a) loses detail. Per test (b) buries the report under ~100 NEEDS DYNAMIC rows.
- Wrong IDs (25/83 citations, 4/5 MASWE) make the report unusable for an audit. The citation checker and the schema are what turn it into evidence, so measure them early.

RISK of my pick: if one control holds both a FAIL and a NO FINDING, the rollup has to be strict (worst child wins, and NO FINDING never covers a MANUAL), or it hides a gap.

I'D VETO: Q1 c. Running the Plan 6 eval with known false-pass analyzers in place produces published numbers we know are wrong.

IDEA: treat repo content (comments, strings, README) that analyzers quote into the report as untrusted. Fence it in the schema as data, and have the citation checker reject any verdict whose quoted text doesn't match the file byte-for-byte at the cited file:line. Prompt-injection steering of a verdict then fails the check.

### Product owner
VOTE: Q1 b, Q2 a, Q3 d (skill+schema, citation checker, must-exist checks, then the small Ward-vs-alone run on the 10 held-out cases; HTML and packaging after that)

WHY:
- PRODUCT.md's success metric is "explicit verdict for more controls, no made-up citations". The skill, the schema and the citation checker produce exactly that. The checker also fixes the MASWE-ID problem at the root, so it doesn't need a separate hardening step first.
- Must-exist checks are the edge the evidence keeps showing. Account deletion was the baseline miss, and the absence cases HO-03 and HO-08 were missed on held-out. They belong in the first eval.
- 24 MASVS controls fit on one screen: "24 controls, 3 FAIL, 12 NO FINDING, 6 NEEDS DYNAMIC…". A hiring manager gets that in a minute. MASTG tests go in as evidence.
- The HTML report overlaps with Plan 8. Packaging can wait, because .mcp.json already runs Ward locally.

RISK of my pick: deferred carry-overs (the 45 KB `dependencies` output, false NO FINDING) could quietly skew the first eval. Cap `dependencies` before that run.

I'D VETO: Q1 c. Carry-overs fixed by looking at held-out failures means tuning on the held-out set, which ADR 0009 forbids. Also Q2 b: 100+ rows, mostly NEEDS DYNAMIC, kills the demo.

IDEA: Make the demo a one-screen terminal summary rendered from the report JSON (count per verdict, plus the "not checked" list). It's free, it's the video shot, and it stands in until Plan 8's UI.

### Hiring manager (persona)
VOTE: Q1 a, Q2 d, Q3 c

WHY:
- In my three minutes, the headline is one number: "Claude alone got 25 of 83 citations wrong. Ward got X." Right now Ward's own run got 4 of 5 MASWE IDs wrong. For a tool that sells "evidence", that's the first thing I'd catch, and it reads as a tutorial copy. Fix it first (1a).
- A false NO FINDING is the worst possible bug for a fintech. Show me those holes closed before you build features on top of them.
- 2d reads like real audit work: verdicts per MASVS control, with test-level detail underneath. 24 rows gives me a summary I can scan. 100+ NEEDS DYNAMIC rows tells me nothing.
- 3c: I'd sooner see a small, honest Ward-vs-alone eval early than a polished HTML report. Anyone can build an HTML report.

RISK of my pick: postponing must-exist checks and packaging leaves Ward looking like a research harness and less like a product people can install.

I'D VETO: 1c. Leaving known citation and false-negative bugs for "the eval to find" shows the team knew about the bugs and shipped anyway. That's a red flag in regulated work.

IDEA: Publish the case where Ward was wrong, next to the cases where it was right, with what changed in between. A visible fix log impresses me more than a high score.

### Developer user (persona)
VOTE: Q1 a, Q2 d, Q3 b

WHY:
- I'd hand the report to an auditor. If one cited ID is wrong (4 of 5 MASWE were wrong on HO-04) or there's one false "NO FINDING", I stop trusting the rest. So hardening comes first, before I ever see a report.
- Auditors think in MASVS controls (24 rows is a page I can read), but they ask "which test?" A per-control verdict with the MASTG tests nested under it covers both. 100+ flat test rows with half of them NEEDS DYNAMIC would bury me.
- Must-exist checks (account deletion, privacy policy, data-deletion URL) are what Play actually rejects me for, and Claude alone misses them. Without them I wouldn't install it.
- Packaging is how I'd use it at all: `/ward:check` in my own repo. An HTML report can wait. JSON plus a markdown summary in the terminal is enough for me now.

RISK of my pick: the hardening step drags on, and the skill still doesn't make the agent call Ward's tools. That's the bigger unknown, and it stays unmeasured for longer.

I'D VETO: Q1 c. Shipping known false-NO-FINDING paths into a pre-audit tool is worse than having no tool, because it gives me false confidence.

IDEA: a "coverage gaps" section at the top of the report: controls Ward couldn't verify and what I'd need to run (dynamic test, manual step). That's the list I'd paste straight into the audit prep ticket.

### Cost and operations
VOTE: Q1 a, Q2 a, Q3 c

WHY:
- Every eval run spends plan usage: 10 held-out runs took about 16 points of the 5-hour window. If `dependencies` still returns 45 KB, or the analyzers still give false NO FINDINGs, those runs measure known bugs and the usage is wasted. Fixing the carry-overs first is cheaper than finding them again through the eval.
- With 24 MASVS controls the report stays small. It is cheap in tokens per run and quick to check by hand. Pinning MASVS also means less upkeep than tracking 100+ MASTG tests, which change from one MASTG release to the next.
- A small Ward-vs-alone eval right after the skill and citation checker answers both open facts (does the agent call the tools, does the schema cut wrong citations) for about one window. It also stops us building the HTML report and packaging on top of a skill that may not work.
- The HTML report and packaging add things to maintain (more surface, release chores) and teach us nothing yet.

RISK of my pick: a verdict per control can hide which test failed. Wrong MASTG evidence inside a control is then harder to grade.

I'D VETO: Q2 b. 100+ test verdicts per run blow past the 25k-token output cap and multiply the cost of every eval trial. Most of them would be NEEDS DYNAMIC noise.

IDEA: a CI test that limits every MCP tool's output to about 20k tokens on fixtures. Also stamp the OSV snapshot date and MASTG version into each report, so data that has gone stale shows up and runs can be reproduced.

**Agree.** Q1 a, 5 of 6. Hardening comes first. Five members veto Q1 c: it would publish numbers we know are wrong, and fixing analyzers from held-out failures counts as tuning on the held-out set. Nobody backs Q2 b; two veto it (the 25k-token cap and NEEDS DYNAMIC noise). The HTML report waits: no one wants it before the eval.

**Split.** Q2: a (24 rows, cheap, demo-friendly) or d (the same 24 rows with tests nested underneath so an auditor can trace them). These are close. d shows the same 24-row summary on top, and the cost member's own risk under a (it can hide which test failed) is exactly what d fixes. Q3: whether must-exist checks come before the first eval (product owner, developer user) or after it (the other four).

**Ideas worth keeping.**
- `report_skeleton` tool (AI engineer): a deterministic skeleton, prefilled with analyzer verdicts and correct MASWE IDs. It cuts the skill-triggering risk and the ID errors at the root.
- A strict rollup rule: worst child wins, and NO FINDING never covers a MANUAL (security).
- The citation checker matches quotes byte for byte at file:line, which doubles as an injection guard (security).
- A "coverage gaps" section at the top of the report (developer user), plus a one-screen terminal summary (product owner).
- A CI cap on each tool's output, and the OSV date and MASTG version stamped on every report (cost and ops).
- A public fix log that shows wrong runs next to right ones (hiring manager).
- Iterate on the example app; run the held-out set once per skill version, logged (AI engineer).

**Recommendation.**
- Q1 a, kept small: put MASWE on every verdict, trim `dependencies` behind the CI size test, and make the false-NO-FINDING SHOULDs give MANUAL. Fixing them fully can wait.
- Q2 d, with the strict rollup, built on `report_skeleton`.
- Q3 c: skill + schema (with skeleton) + citation checker. Develop on the example app, then run one Ward arm on the 10 held-out cases (the alone arm already exists, so 10 runs, about 16 points of the window). Must-exist checks follow right after: of the absence cases, HO-03 and HO-08 aren't account deletion or a privacy link, so the first eval loses little. Then packaging, then a run on Karlo's app. The HTML report goes to Plan 8.
